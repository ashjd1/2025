terraform core and workflow

	Work flow as below.
	the actual terraform workflow consiste of write plan and apply only

	write        -> write main.tf
	initialize   -> all the required modules are insatlled here, line if you mention the aws, then aws modules will be insatlled
	plan         -> review the changes or creating infra
	apply        -> make reviewed changes.
	destroy      -> delete what evey you have created.
	validate     -> check syntex error befor apply or plan command

	## init
	After the "$ terraform init" command you will see .terraform dir in same dir, in that .terraform DIR you can see provider and modules folders, when you run the init command all the binaries related to the provider and modules with provided versin are download from github or internet to these folders and get accessed from there.

	## plan
		Its a dry run
		In plan command you will see what changes will be made in infra, but there will not be any actual change there, you will see added with + updatated with ~ and removed with -

		You can save the plan with "$ terraform plan -out=mynewplan.tfplan" command, and you can use that .tfplan file to apply the changes whenever you want, even the monthes later. "$ terraform apply mynewplan.tfplan".

		when you run the plan command you will get the output as + - and ~ which is resources are added remove and updated, so when you run apply command terraform comapre the desired state and curr state, and create that output.

		by default terraform can manage 10 resource at a time in parallel and you can manage the paraller execution count with -parallelism=5 parameter.

	## apply
		state filw will be locaed which apply command is running, to prevent the concurrent edits

		No rollback once applied

		apply command 1st runs the plan command, show you what are the changes then you need to conform with "Y", then resources will be created.

		If you have saved the plan commands file "mynewplan.tfplan" then you can run with "$ terraforma apply mynewplan.tfplan" this just skipps the plan process and direcly applied the changes.

		-auto-approve can skip the "yes or no" thing and direcly apply the changes, useful for pipeline

		-input=false -> same thing as above.

		when you use apply command then your resource will be created as per configuration then state file will be created and maintain the record

	## Destroy
		exactly like apply command, just a reverce, restory command just redtory the created resource,

		you can selectively delet any block, just delete from the tf file and use "apply" command, the configuration which you removed that will be deleted.

		you can delete any resource selectively with -target=<resource name> command.
		"$ terraform destory -target=<resource name>"
		when you use the -target option then make sure to remove the configuration from the .tf file as well, because if you run apply command then terraform will create that deleted resource.

		once terraform remove all the resource from cloud then it update the state file and you will have empty state file as there is nothing in cloud from terraform.
		
	## validate
		validate is just to check if the code which you have writtne is valide or is there nay syntex error or not, its not relatade to any king of cloud or state file, just a syntex

StateFile: -
	Terraform statefile is memory of terraform, when you create the any resources, when resource is created successfully that time statefile is updatated, and whenever you make some changes in your code, and apply those chages, terraform compare with the stateFile and current configuration and make the changes.
	
	## State Lock file
	when multiple developers are working on single project, when we use apply command other developer might chaange code, and developer might not get expected result, so when we have state file, terraform creates state lockfile as well, so that we dont mess in configuration.
	
	## remote statefile
	now you know howmuch statefile is iportant, so we need to keep is safe and only accessable to who has creadiblity so we can store at remote location, like s3 bucket, or storage.
	
	terraform {
	backend "s3" { ## store the state file in s3 bucket
	bucket = <bucket name>
	key = <path/name-of-stateFile>
	region = "us-east-1"
	use_locakfile = true
	}
	}
	
	we can use the "$ terraform init -migrate-state" command to move to the locak state file to the backend
	
	## Managing State file
		for managing the statefile, terraform gives some command.
		"$ terraform state list"
		"$ terraform state show"
		
		List command: - lists the all resources which are mentioned and managed in the statefile.
		Show command: - can be used two different ways "$ terraform show" "$ terraform state show <resoucre-name>", in 1st show command terraform just dumps the whole stateFile with too much details and in human readable format, if you use the state show <resoucre-name> command then terraform gives the all details about that resource in human readable format.
		
		check on below commands
		"$ terraform state mv"
		"$ terraform state rm"
		"$ terraform state pull/push"
	
	## Terraform Drifft: -
		Consider a senior where, you have created resource with terraform, but after sometime one developer make changes in resource without touching the terraform configuration.
		and if you run plan command in this situation, stateFile knows that configuration is not matching with resource, that situation called as state driffet
		
		so there are two solutions to solve this either accept changes and make changes in configuration, or run apply command and make changes in resources.
		
		so 2nd option is prety stateforward, for 1st option, yuo will need to use "$ terraform apply -refresh-only" command, -refresh-only option make cahnages in current state file, then you will need to configururation from .tf file. 
		
		we can use -refresh-only option with apply and plan command, so plan command will just show what will happen, just like plan do, and apply command will actully change the stateFile.

Managing the resource behavior and dependencies

	## depends_on
		Consider you are deploying the web-server which has back-endpserver which is some sort of DB, so to work the web-server properly we need to configure the DB server 1st then we can deploy the web-server.
		So we can handel these kind of dependencies we have a "depends_on"
		
		there are two type to mention the dependencies, implicite or explicite.
		in implicite, just mention the block which you need to use, like 
		"$ subnet_id = <resource>.<name>.<id>"
		with above line we tell terraform that we need to create this resource for current resouce
		
		and in explicite method we add [depends_on] block.
		
	## lifecycle{}
		lifecycle is basecly, instruction for the terraform, what to do what not to do, with this block.
		we have to mention the lifecycle in any resouce block only.
		so
		
		lifecycle {
		destroy = false                           		 	 -> will not distroy.
		ignore_changes = <resource-name>.<part>   		 	 -> will ignore changes made in infra, otherwise it will be reconfigured or recreated. 
		create_before_destroy = true              		 	 -> will create new resource before destroying 
		prevent_destroy = true                    		 	 -> will not distroy at any cost.
		replace_trigger_by [anothre_resource]     		 	 -> will delete and recreate the existing resorce if make changes in "anothre_resource"
		precondition {condition == var.mv.name == "ashu"     -> before create current resource condition must get satisfied, otherwise error message 
					  error_message = "name is not matching"    will get printed.
		}  
		postcondition										 -> similar to precondition, just check the condtion after resource created.
		}
		
Security Configuration
	even of we cofigre the secrtets in env vrtiable still while execution the secrtets will endsup in state file or may be in CI/CD logs in other files, so we need to manage it well
	
	Sensitive: -
		So 1s level, very basic
		Whenever you are creating variable block in tf file, you can add "sensitive = true" to that block, so that when you run terraform plan, apply it will not be displaed on screen or will not carry as it is in log files
		But still you have hard coded your password in tf file, not good practice.
		
		variable "db_pass"{
		description = "This is pass for DB"
		type = string
		sensitive = true
		}
		
	ENV_VERIABLE: -
		So in above explanation we see how we can mark it as sensitive and hind from logs and CMD, but will we are writing the pass in tf file, not sure.
		But if you write the pass in "TF_VAR_db_pass", then this will be only accessable to environmet only as its a evn variable, also there is no rish with commit pass directly in github.
		you can combine the variable section with env variable and make it more secure.
		Also if your whole setup in on github, then you can use githubs secret to set veriable 
		"$ TF_VAR_db_pass: ${{ secrets.BD_PASS }}"

	| Technique                 | Protects Logs/Output? | Protects State? | Protects Git Commits? | Best For                                       |
	| ------------------------- | --------------------- | --------------- | --------------------- | ---------------------------------------------- |
	| **Sensitive Variables**   | ✅ Yes                | ❌ No           | ❌ No                | Hiding output, marking intent                  |
	| **Environment Variables** | ✨ Partial            | ❌ No           | ✅ Yes               | Local dev, CI/CD, keeping secrets out of files |
	| **External Sources**      | ✨ Partial            | ⚠️ Reduces      | ✅ Yes               | Production secrets, centralized management     |

	Enphemeral values: -
		Even after all the above techinic we have sensitive data in the statefile, so we can use the enphemeral as true whcih will tell tarraform to omit this parater to record while the plan and apply action.
		
		variable "db_pass" {
			sensitive = true
			enphemeral = true
		} 
		
		we can use enphemeral in these blocks: - local value, provider, resources, variable, output, provisioner.
		So we cant use the enphemeral veriables direcly, because while plan and apply command these values gets omited and due to missing values you will get the error.
		so we have enphemeral block, which will fetch the data at runtime and store in memory, not get stored in statefile and cleared just after the operation is completed.
		
		
		data "aws_secretmanager_secret_version" "db_pass"{
			secret_id = "production/database/password"
		}
	
		### insted of data block we use enphemeral block, that the only diff here.
		enphemeral "aws_secretmanager_secret_version" "db_pass"{
			secret_id = "production/database/password"
		}
		
Debuggeing: -
	To enable logs we need to set the env variable, which is "TF_LOG=TRACE", then any terraform command will be executed with in detailed logs.
	
	levels of verbosity
	TRACE -> too much details 
	DEBUG -> -1
	INFO  -> -1
	WARN  -> omly warning
	ERROR -> only error
	
	To enable only the core opearation logs we have "TF_LOG_CORE=trace"
	$ TF_LOG_PROVIDERS=TRACE           -> logs only from the provoder block
	$ TF_LOG_PATH=/path/to/logFile.log -> to sore the logs in specific file.
	$ unset TF_LOG                     -> to remove the logenablement
	
HCP terraform: -

	hcp has everything that you might need to create resource and run the terraform.
	
	it manages mostof the things, like state file, tf configuration, access control and many more.
	
	you can consider it as running terraform on cloud platform.
	
	To connect local macine to hcp, we can use "$ terraform login" command and use token to access.
	For automation we can use the "$ TF_VAR_app_terraform_io=<token>" env veriable to store the token and loging automateclly.
